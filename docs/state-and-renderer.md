# 状態更新とレンダラーへの同期

通常の編集では、変更対象の定義だけをレンダラーへ送ります。通信量の削減と、描画キャッシュ・実行インスタンスの再利用は別の関心として扱います。頻繁なパラメータ調整を効率化しつつ、構造変更などでは対象Module・レイヤー単位の無効化を許容して実装を単純に保ちます。

## 責務と変更通知

- 正となるプロジェクト状態はUIの `ProjectContext` が `ProjectState` として所有します。Commandは状態の変更とUndo/Redoを担当し、変更後に対象IDと編集内容を `AppStateChange` として通知します。レンダラーでCommandを再実行したり、ID発行・配線修復・時刻の丸めを再度行ったりしません。
- Commandと汎用の `UndoRedo` は同期先を知りません。`ProjectContext.stateManager.onChange()` の購読側が必要な通知を選びます。通常実行・Undo・Redo・履歴へのマージを伴う連続編集は、同じ通知経路を通します。
- 通知は「値・入力種別・接続・配列要素・リセット」「バイパス・解像度」「レイヤー定義・クリップ」など、ドメイン上の変更を表します。Commandや通信型に `preserveCache` / `preserveModuleInstance` のようなレンダラーの保持方針を含めません。
- `RendererProjectSynchronizer` は通知の集約と、確定済み状態から送信データを取り出す役割を持ちます。キャッシュ・インスタンスの保持判断は、レンダラー内の [project-change-policy.ts](./packages/renderer/src/project-change-policy.ts) に集約します。各Managerが対象の特定や変更世代の管理を行い、`VisualModuleRenderer` はModule内部の評価とキャッシュを扱います。汎用の `TimelineRenderer` には実行インスタンスの更新判定に必要な世代を渡し、Commandの種類を解釈させません。
- 型も同じ責務に分けます。`ParameterChangeKind` はparameter、`VisualModuleNodeChange` はvisual-module、`TimelineLayerChange` はtimelineが所有します。登録Moduleとinline Moduleの所在を表す `VisualModuleTarget` はproject、UIの通知契約 `AppStateChange` はuiが所有します。子ドメインから同期クラスやプロジェクト内の配置へ依存させません。

## 転送単位とバッチ

- 初期化・プロジェクト読み込み・同期復旧では、Visual Module一覧とScene一覧の全量スナップショットを使います。`replaceProjectState()` はこの置換境界であり、同じIDでも旧プロジェクトの履歴を引き継ぎません。通常の編集には `applyProjectChanges()` を使い、Module・Scene全体のdeep watchで `updateDynamicOptions()` に全一覧を送り直しません。
- ノード編集はノード全体、レイヤー編集はレイヤー全体、ノードの追加・削除・順序変更やModuleの公開入出力変更は対象Module全体を送ります。Scene自体の追加・削除・解像度変更などは対象Scene、レイヤー順序変更はそのSceneのレイヤーID列を送ります。パラメータの末端ごとの汎用patchプロトコルにはしません。
- 次のmicrotaskで送信するまでに集まった変更は対象ごとにまとめ、送信時の最終状態を取得します。ただし、変更種別は途中のものも保持します。例えば、接続変更の後に値を変更しても、値だけの編集として扱ってはいけません。
- Module全体の更新は内部ノードの更新を、Scene全体の更新は内部の更新を吸収します。レイヤーの追加・削除・置換も内部inline Moduleの更新を吸収しますが、レイヤーの引数編集とinline Module内部の編集では両方の変更種別を残します。レイヤーの追加・削除を反映してから最終的な順序を適用します。
- 登録ModuleはModule ID、inline ModuleはScene IDとレイヤーIDで指定します。登録Moduleの編集は、その定義を使うVisual Module Live Previewと各タイムライン配置へ反映します。inline Moduleの編集対象は指定されたレイヤーの定義です。同じ定義を使っていても、実行状態は配置・クリップごとに独立させます。
- 現在、タイムラインのModule引数編集もレイヤー全体を送るため、inline Moduleでは内部定義も転送されます。Visual Module Live Previewの引数更新は `updateVisualModuleLivePreviewParamValues()` を使い、同じModuleの値調整でVisual Module Live Previewを開始し直しません。

## 描画キャッシュと実行インスタンス

描画キャッシュの無効化は、次回にエフェクトの描画をスキップできなくすることです。エフェクトの実行インスタンス・GPUリソース・履歴を破棄することとは区別します。

| 変更 | キャッシュ・インスタンスの扱い |
| --- | --- |
| Module内ノードの通常のパラメータ値 | 既存の出力キャッシュキーとインスタンスを保持し、再評価後のキーが変化したノードと、その出力に依存する後段だけ再描画する |
| Module内ノードの静的設定・入力種別・接続・配列要素の追加削除・リセット・バイパス・解像度 | 対象Moduleの全エフェクトを破棄・再作成し、未編集ノードの履歴と描画キャッシュもリセットする |
| ノードの追加削除・順序変更、Moduleの公開パラメータ・入出力など | 対象Moduleの全エフェクトを破棄・再作成する。同じID・種類の既存ノードも保持しない |
| タイムラインのModule引数の通常の値 | 配置のインスタンスと出力キャッシュキーを保持し、内部ノードの評価結果から再描画を判定する |
| エフェクトレイヤーのパラメータ、合成設定、クリップ、レイヤー解像度、Module引数の入力種別・配列構造・リセットなど | 対象レイヤーの実行インスタンスを再作成し、履歴をリセットする。他のレイヤーは保持する。Scene配置を再作成する場合は、その配下の再作成を許容する |
| レイヤー順序 | インスタンスを保持し、新しい順序・下層入力で評価と合成を行う |
| Scene定義の置換・解像度変更 | そのSceneの各配置と配下のインスタンスを再作成する。Scene内部のノード・レイヤー編集は、それぞれの更新単位で扱う |

- 通常の値編集には、リテラル値・式の本文・パラメータ内のキーやinline automationの内容・配列やstruct内の末端の値を含めます。Bindingの入力種別切り替え、接続先やサンプリング設定の変更、配列構造変更、リセットとは区別します。
- 静的な `A → B → C` でBの値だけを変えた場合、Aの描画結果を再利用し、BとCを再描画します。無関係な枝も保持します。式を編集しても評価結果が同じなら、再描画は不要です。判定には評価済みパラメータ、上流の出力キー、解像度、エフェクトの `cacheVersion`・リソース世代などを使います。
- Inノードのuniform入力は参照した出力ポートと値で比較します。外部から借用したテクスチャは同じ `GPUTexture` の内容が変わり得るため、それに依存する枝は保守的に再描画します。時間・動画・音声・履歴処理や `disableCache` に由来する再描画も、値編集による無効化とは別に扱います。
- 子Scene内部の編集だけで、親のScene配置や無関係な子レイヤーを作り直しません。各配置は最新の定義を参照し、必要な対象だけを更新します。定義の変更世代と描画・GPUリソースの世代は分離し、未反映の構造変更の後に値編集が来ても、必要なキャッシュ無効化を失わないようにします。
- Module内のパラメータの再評価やキャッシュキーの再計算、タイムライン全体の再合成は許容します。これらを、全ノードのGPU再描画やタイムライン全インスタンスの再作成と混同しないでください。通常のパラメータ調整を理由に全タイムラインを破棄しません。

## 適用・初期化・復旧

Timelineのレイヤー検証では、レイヤー自身の区間・解像度・固有設定とパラメータの検証を分けます。パラメータの構造・入力方式の検証と参照収集は一度のツリー走査で行います。Scene追加・階層編集Commandは全Sceneを適用前に再検証せず、静的診断の更新を変更通知の受信側へ集約します。

- 静的検証はUIの`ProjectRenderValidation`が設定変更の通知内で同期的に行います。ノード・レイヤー単位の静的な形と診断を保持し、通常のliteral値・式本文が変わっても構造や参照が同じなら再検証しません。接続グラフの循環検査は辺の構成変更時だけ行います。登録Visual Module・Asset・Sceneなどの参照先変更は利用箇所の索引から再検証します。
- 静的エラーが一つでもあれば、未使用のVisual Moduleや無効な枝のエラーも含めてプロジェクト全体の描画を停止します。UIは不正な編集状態も保持しますが、レンダラーには送りません。レンダラーは検証済み設定を受け取る契約で、描画・準備・音声計画での構造の再検証は行いません。
- `PreviewRenderEngine`は静的・実行時の失敗で両プレビューのエンジンを破棄します。静的エラーが解消した設定変更、実行時失敗後の描画に関係する設定変更、またはPreviewの再試行操作で最新スナップショットから生成します。エラー中の差分を蓄積・再送せず、描画履歴はリセットします。時刻の経過だけでは再試行しません。
- 更新前の非同期フレームは中断・世代確認で無効化します。古い描画やリソース準備の完了が、更新後の状態や出力を上書きしてはいけません。実行中フレームの中断と、保持するキャッシュ・履歴の破棄は別に扱います。
- ControllerはWorker不在・初期化中でも最新の送信予定状態を保持します。初期スナップショットの取得以前の変更はそのスナップショットに含め、取得後の差分だけを順番に送ります。初期化に含まれた差分を重複適用しません。Workerの再作成・破棄をまたぐ古い応答も世代で除外します。
- 初回起動と破棄後の再生成は`relaunchManager()`に統一します。レンダラーの`renderError`は失敗のみを通知し、Controllerのエラー表示は新しいManagerの初期化完了で解除します。Timelineのレイヤー状態には描画エラーを保持せず、Managerの破棄時にノード・レイヤーの状態をまとめて解除します。
- 差分適用のRPCが失敗した場合もエンジンを破棄します。静的診断と実行時失敗は別に保持し、古いWorkerの成功通知で解除しません。UI側Commandのロールバックは行いません。
- 失敗の通知はControllerとSynchronizerが行い、両エンジンの破棄は`PreviewRenderEngine`が調整します。Synchronizerは差分失敗後の全量同期を行わず、再試行時の最新スナップショット取り込みに復旧を集約します。
- 静的診断の解除とプレビュー固有設定の変更も、同じ再試行予約を使います。同じ編集の複数通知はまとめ、予約後に発生した失敗や停止を古い予約で解除しません。Inline Visual Moduleの公開定義変更では、Bindingの形が同じでも所有レイヤーの引数を再検証します。
- 差分の反映後にプレビューを更新します。新規Sceneを選択する場合など、後続操作が変更対象の存在に依存するときは、同期の `flush()` 完了を待ちます。

## 専用の同期経路と現在の制約

書き出しはUIの静的検証結果で開始を制御し、開始時にプロジェクト全体を再検証しません。同じ正常な設定のスナップショットを専用Workerへ渡します。書き出し専用の出力設定、素材取得、GPUの実際の上限、エンコーダーなどの実行時検証は残します。

- Assets・Playersの定義はManagerの初期化メッセージの`resources`で渡し、インスタンスの寿命中に変更しません。素材・Playerの追加・削除・参照先変更では、UIが同期的に両プレビューを停止・破棄し、参照解決後の最新状態から再生成します。Subsystemでも素材一覧・メタデータ・画像テクスチャは不変です。初期素材のGPU準備はManagerの`ready`で待ち、プレビュー・書き出しとも準備完了後に描画を開始します。プロジェクト解像度・表示設定は同期処理の`updateDynamicOptions()`で反映します。
- Scene名・レイヤー名の通知は描画の差分同期では無視します。素材・Playerの表示名やサムネイルだけの変更、同値の素材情報の再代入でも再生成しません。素材変更による再生成では、GPUリソース・描画キャッシュ・エフェクト履歴を引き継ぎません。
- 音声の同期は音声に影響する状態を対象とし、通常の映像パラメータ編集で音声再生を開始し直しません。
