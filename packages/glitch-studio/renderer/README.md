Glitch Studioとして、各subsystemのレンダラーを利用する統括層

Glitch Studioのドメイン知識を持っていてもよい

`TimelineAudioInputs`は波形・スペクトラム描画用の音声入力を統括する。Assetからファイルを解決し、Audio subsystemのデコーダー・PCMキャッシュとTimeline Audio Rendererを接続する。再生Workerとは独立した読み出しを使い、同じデコーダーへの並行seekは直列化する。音声計画は取得元Scene・下層/指定レイヤーの方式・レイヤーIDごとに保持する。Scene定義の更新時に音声計画、Asset更新時にデコードキャッシュを無効化する。指定先が同じSceneにない、または音声出力を持たない場合は入力なしを返し、別Sceneへ探しに行かない。古い入力の完了は中断された描画へ採用せず、実行中の読み出しが終わってからデコーダーを解放する。

描画要求のキャンセルは読み出しキューとAudio subsystemへ伝える。実行前に中断された読み出しをスキップし、実行中の処理もデコードブロック・窓・クリップの境界で終了する。中断した要求のために後続の素材を読み続けない。

`PlayerAudioInputs`はLIVEのPlayer指定を解決し、取得元の履歴状態ごとに固定した`AudioInput`を共有する。同じ入力を読む複数ノードや履歴の変わらない描画ではPCMを再複製しない。追記・リセット・取得元の差し替えは新しいスナップショットにし、過去の入力が参照するPCMは変更しない。Visual Moduleには`resolveAudioSource`を注入し、Player指定の解釈とスナップショットの所有をGlitch Studio側に保つ。

タイムラインの`timelineFps`と`timelineMotionBlur`は`TimelineRendererManager`のstatic optionsとして初期化時に確定する。変更時はUI側のControllerがWorkerごと再生成し、キャッシュ・エフェクトの履歴・蓄積用GPUリソースを引き継がない。fpsとブラー設定の同時適用は1回にまとめ、再生成中の後続変更も最新値まで反映する。

プレビュー用のサンプル数はUIがプロジェクトと別に所有する。UIはプレビュー用Managerを作る際に`timelineMotionBlur.samples`をUIの選択値で上書きし、書き出し用Managerには保存されたプロジェクトのサンプル数を渡す。レンダラーはプレビュー専用のサンプル数フィールドやプロジェクトの既定値を持たない。

プレビューfps倍率は描画要求の頻度だけを変更するUI側の設定で、再生成を必要としない。動画書き出しでは呼び出し側が指定したfpsを露光時間の基準に使い、静止画とプレビューではstatic optionsの`timelineFps`を使う。ブラー無効・シャッター角0・サンプル数0/1の場合は`TimelineRenderer.renderAt()`で単発描画し、複数サンプル用の管理を経由しない。

タイムラインのプレビューは、再生・シーク・一時停止とも`TimelinePreviewScheduler`へ渡し、GPU完了待ちを含めて1フレームだけを処理する。待機要求は最新の時刻へ上書きし、進行中のフレームは通常のシークでは中断しない。音声時計・再生時刻はUI側で進め続け、映像だけ中間フレームを飛ばす。シーク先が表示されるまで描画済みの画像を保ち、進行中だった古い時刻の画像が一時的に表示されることは許容する。

GPUを所有するManagerが、最終表示とモーションブラーの全サンプルをsubmitした後に`queue.onSubmittedWorkDone()`を待つ。途中の失敗や編集による中断でも送信済み処理を待ち、編集・Scene切り替えで待機要求を破棄しても同時処理の制限は解除しない。書き出し用の`renderTimelineFrame()`はこのスケジューラーを経由せず、呼び出し側が全フレームを順番に描画・エンコードする。

注意する必要があるのは、すべてのサブシステムは公平だということです。

TimelineはVisual Moduleを使用し、Visual ModuleはEffectを使用するという依存の階層構造自体はあるが、それは「Glitch Studioにおいてはタイムラインがメイン機能であり、タイムラインがすべてをk管理する」などということは意味せず、Glitch Studio自体の設計とは全く関係がない。
